Current responsibility: develop ExtendCodeAgent for OpenCode and evaluate/fix coexistence with OMO. Do not implement ControlDeck installation/UI/stack-management logic here.

Preserve the host-neutral Project Intelligence core, keep OpenCode-specific behavior in its adapter, reuse existing components before adding new ones, and require real OpenCode/agent/LLM evidence before promoting a capability, capability depth, targeted-verification policy, Test Portfolio capability, compositional-evidence policy, failure-reevaluation policy, integrated verification capability, or an ECA+OMO version tuple.

Strengthened PI capabilities must remain depth-configurable rather than permanently maximum-cost. Keep rollout authority (`off/shadow/advisory/active`) separate from per-capability execution depth, and use evaluation evidence to recommend/promote/demote levels.

**Feature portfolio economy and interaction-aware adoption.** Large implementation volume is not a reason to accumulate mechanisms. Before adding a feature, identify the existing owner and prefer reuse, extension, folding or consolidation over a parallel implementation. Build the smallest evaluable slice first. At the relevant evidence gate, give each new or strengthened mechanism a portfolio disposition such as `KEEP`, `CONSOLIDATE`, `OFF_BY_DEFAULT`, `DEFER`, `REMOVE`, or `SUBSTRATE_ONLY`; these are planning dispositions, not new `CapabilityName` values. Evaluate interaction carefully but do not run an exhaustive power set: measure standalone marginal effect when meaningful, then the smallest mechanism-based bundle expected to work, then leave-one-out ablation of a successful bundle, and only then targeted pairwise/higher-order interactions with a predeclared causal rationale. A null standalone result is not enough to delete a plausible prerequisite: if the successful bundle degrades when that mechanism is removed, classify it `SUBSTRATE_ONLY` and keep it internal without claiming independent product value. Conversely, if removal does not degrade quality/coverage and reduces latency, context, memory, dependencies or maintenance complexity, consolidate or disable/remove the redundant path. If a mechanism has neither marginal nor conditional contribution after bounded interaction testing, keep it off/deferred or remove it rather than carrying speculative cost. Negative interactions should produce mutually exclusive routing, narrower scope or OFF defaults rather than forcing both mechanisms on. Record the winning bundle and the rejected/merged mechanisms so later stages do not reintroduce them accidentally.

**Multi-objective effect rule.** Quality improvement is not the only valid effect. If task/oracle correctness, critical-evidence coverage, required verification and false-sufficient behavior remain non-inferior, a meaningful reduction in context, input tokens, wall time, RAM/VRAM, model/tool calls or operational burden counts as a positive PI effect. Conversely, do not call context compression a win when the benefit is merely shifted into large preprocessing latency, primary-model contention, model eviction/reload, a smaller usable coding-model context, fragile API/model dependencies, or other disproportionate cost. Evaluate an explicit effect vector rather than one weighted score, using same-head paired distributions where possible. For C2 use `docs/evaluation/c2-effect-metrics-v1.json`: it defines quality hard gates, provisional meaningful/strong context reductions, default/scoped latency budgets, feasibility gains, reject conditions and interaction-aware bundle rules. These thresholds are predeclared engineering gates, not immutable truths; change them only with recorded evidence before the run whose result they govern.

ECA development must dogfood the Master Plan's Minimum Sufficient Reasoning invariant. Before spending an **auxiliary PI model** call, first determine whether deterministic analysis, sealed evidence, compatible prior results, PI-only preflight, or a narrower task/depth/context can resolve the decision. Start with the minimum sufficient capability, depth and context, expand only for an explicit unresolved Evidence Gap, and do not repeat identical model work unless an evaluation contract explicitly requires independent repetition. Call reduction never permits skipping required correctness evidence or treating untested work as no effect.

**Primary coding model vs auxiliary PI model.** Do not confuse the host's primary task/coding model with an optional model embedded inside PI. OpenCode's primary model (for example the configured Qwen coding model) is expected to perform code generation, design, repair and genuinely model-required reasoning, and may be used as often as the task/evaluation contract needs. It does not require a separate feature-adoption proof merely because it is a model. Avoid pointless duplicate calls, but do not suppress useful coding/reasoning work just to minimize call count. By contrast, an **auxiliary PI model** means an extra classifier, ranker/reranker, summarizer, schema projector, judge/validator, planner, or similar inference component added by ECA. These carry extra startup/API/VRAM/RAM/latency/operational cost and default to disabled unless they win an evidence-based adoption test.

**Auxiliary-model adoption gate.** Do not add an auxiliary PI model merely because it is convenient. First build and measure the deterministic/non-LLM baseline. An auxiliary model may be adopted only when a predeclared comparative evaluation shows a material quality gain that justifies its startup, API, memory/VRAM, latency and token/resource cost, with no unacceptable regression in correctness, critical-evidence recall, false-sufficient rate, privacy, or required verification. Record model/provider scope, calls, context/tokens, startup/residency requirements where observable, peak resource impact where observable, and wall time. If the auxiliary model does not win, keep it disabled; if it wins only for a bounded task class, enable it only there. A very fast/small auxiliary model may be acceptable even without a large speed win when its operational footprint is negligible and quality is non-inferior, but this must still be measured. Correctness evidence outranks raw call reduction.

For C2 specifically, also read `docs/handoff/C2_EVIDENCE_DELIVERY_DECISION.md`. It is a stage-local architecture decision, not a second roadmap. Preserve protected/mandatory truth before optimizing context; use deterministic sufficiency and evidence-utilization checks; treat rankers/rerankers as optional shadow components until they beat the deterministic baseline; and never count `not in model context` as `not known by ECA`.

For verification, treat `docs/VERIFICATION_OBLIGATION_AND_TEST_EXECUTION_PLAN.md` as authoritative when older shorthand suggests a simple `direct -> impacted -> subsystem -> full` test ladder. Determine **what must be verified** from the semantic change, Impact closure, requirements and evidence coverage; then optimize **how to execute the required verification set** using duration/setup/parallelism data. Additional tests are driven by residual uncovered/conflicted obligations, not by a vague time-budget or "enough tests have passed" rule. Full-suite runs remain available for release/fallback/high-uncertainty cases and periodic calibration of PI misses.

For existing repositories, use the Test Portfolio plan's bootstrap model: first import a revision-aware initial Project/Twin/test baseline, but never treat that baseline as verified correctness. Test Intelligence may then audit, design, generate/update, evaluate, select and consolidate tests as evidence providers.

GUI verification must prove the required **user-visible/runtime outcome**, not merely DOM render/click success. For cross-boundary actions, model and verify the causal flow from UI action through state/API/IPC/backend/process/resource effects to the final observable state. Keep browser/runtime execution owned by the host; ECA owns the Project Intelligence/verification obligations and evidence interpretation.

For expensive verification, follow `docs/COMPOSITIONAL_VERIFICATION_AND_EVIDENCE_REUSE_PLAN.md`: evidence reuse is not a generic PASS cache. Reuse a prior segment only when its Evidence Dependency Closure, boundary pre/postconditions, runtime/config/environment assumptions, revision/workspace identity and freshness remain compatible. Model user-flow verification as a branching Evidence DAG rather than forcing a linear chain. Find the nearest trustworthy Verification Frontier, verify only residual invalidated/uncovered obligations, and compose fresh + reusable evidence conservatively. Preserve periodic/release full E2E calibration so hidden dependencies and composition misses remain discoverable.

For unexpected verification failures, follow `docs/FAILURE_DRIVEN_PI_REEVALUATION_PLAN.md`. Treat FAIL as new revision-aware evidence, not automatic proof of production-code error or test obsolescence. Re-evaluate in this order by default: **Test Intent/specification consistency -> Oracle quality -> fixture/mock/helper freshness -> harness/environment/runtime validity -> Impact/Evidence Dependency Closure -> static/runtime reconciliation -> production implementation**. Failure alone must never justify deleting, weakening or obsoleting a test. Expand only the relevant PI capability/scope when current evidence is insufficient, and record `PI_MODEL_MISS` / `EVIDENCE_REUSE_MISS` as product calibration evidence.

For the next verification refinements, follow `docs/PI_VERIFICATION_OBSERVABILITY_INTEGRATED_DESIGN.md`. Do not build standalone competing truth stores for Observability Gap, Environment Matrix, Verification Certificate, Nondeterminism, Evidence Diversity, Regression Knowledge, Performance Obligations, or Verification Debt. Project them from the same revision-aware Digital Twin / Project Graph / Impact / Test Intent / Runtime Evidence / Traceability / Convergence model. Missing observability is not automatically a missing test; environment verification must be impact-selected rather than Cartesian; certificates are auditable reason records rather than permanent proof; and Evidence Diversity must protect independent unit/contract/runtime/GUI/calibration value during test consolidation.
